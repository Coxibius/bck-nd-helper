# PRD-250 — PRD Intelligence

## Executive Summary

Backend Helper already explains the current technical shape of a software project and can inject versioned user stories, acceptance criteria, and business rules into AI context. It does not yet provide the product-level intent that explains why the project or feature exists, who it serves, what outcomes matter, and what must deliberately remain outside the scope.

Version 2.5.0 will introduce a lightweight, local-first Product Requirements Document layer. Humans will author product intent in version-controlled Markdown files. Backend Helper will parse, validate, link, and render that intent for developers, AI agents, and CI pipelines without attempting to invent business decisions from source code.

The release is intentionally narrow: PRD Intelligence is a context compiler and trust layer, not a project-management platform or an autonomous product manager.

## Problem Statement

AI coding agents can inspect source code and receive detailed implementation requirements while still making product-incoherent decisions. Code reveals what exists, and user stories describe individual behavior, but neither reliably communicates:

- The product problem being solved.
- The intended users and their constraints.
- The desired outcomes and success measures.
- The boundaries of the release.
- Explicit non-goals and accepted trade-offs.
- Unresolved product questions that an agent must not guess.

This gap is especially costly for students and developers who move between free or short-lived AI sessions. Each new agent must reconstruct intent from incomplete prompts, consuming tokens and increasing hallucination risk. It also limits future adoption in professional teams, where unverified assumptions and missing provenance reduce trust.

## Product Principle

> Humans declare intent. Backend Helper structures, validates, links, and delivers it.

Backend Helper may detect missing information or contradictions, but it must not infer or silently generate target users, product goals, success metrics, non-goals, or business intent from source code.

## Target Users

### Primary users

1. **Students using multiple AI agents**
   - Need to preserve product intent between short or token-limited conversations.
   - Need guided structure without learning a large product-management platform.
   - Need professional practices that remain understandable and local.

2. **Educators teaching software engineering**
   - Need a concrete bridge between product analysis, requirements, implementation, and testing.
   - Need versionable artifacts that can be reviewed in assignments.
   - Need deterministic validation rather than subjective AI-generated grading.

3. **Open-source developers and small teams**
   - Need lightweight product context alongside the repository.
   - Need AI agents to respect scope and business intent without adopting Jira or Confluence.

### Secondary users

4. **Enterprise engineering teams evaluating governed AI workflows**
   - Need explicit, reviewable context with source provenance.
   - Need offline operation and control over what context is shared.
   - Enterprise policy, permissions, and secret-governance capabilities are not part of this release.

## Jobs to Be Done

- When I begin a project or feature, help me capture product intent in a professional structure without requiring a separate platform.
- When I hand work to a new AI agent, provide the approved product intent before implementation details so the agent does not invent scope.
- When I review a project, tell me which important product fields or requirement references are missing.
- When I run CI, provide deterministic machine-readable diagnostics for invalid product context.
- When no PRD exists, preserve the current Backend Helper workflow without noise or failure.

## Goals

### G1 — Version-controlled product intent

Provide a human-readable PRD format stored inside `.bck-nd/product/` and suitable for Git review.

### G2 — Deterministic validation

Detect structural omissions, invalid states, duplicate identifiers, broken requirement references, and release-readiness problems without an AI provider.

### G3 — Requirements linkage

Link product-level scope to existing Requirement Intelligence through explicit requirement IDs, without changing existing requirement files in the MVP.

### G4 — Efficient agent context

Expose a stable `<product_context>` representation to one-shot prompts and MCP consumers while preserving Backend Helper's token-efficiency mission.

### G5 — Lightweight and backward-compatible delivery

Remain offline-first, add no heavyweight dependency, and leave projects without `.bck-nd/product/` behaviorally unchanged.

## Non-Goals

Version 2.5.0 will not:

- Generate or approve product intent autonomously with AI.
- Infer users, goals, metrics, or non-goals from source code.
- Replace Jira, Confluence, Linear, Notion, or another project-management platform.
- Provide a collaborative visual PRD editor.
- Introduce accounts, cloud storage, telemetry, or synchronization.
- Add ADR, RFC, design-document, threat-model, SLO, or runbook management.
- Add product nodes to the technical Abstract Semantic Graph.
- Build the complete PRD-to-code-to-test traceability graph.
- Modify existing requirement files automatically.
- Add PRD content to the generated offline HTML documentation portal.
- Provide enterprise permissions, policy enforcement, or secret-management features.

## Proposed User Experience

### Create a PRD

```console
bck-nd prd init
bck-nd prd init PRD-AUTH
```

With no identifier, the command creates `.bck-nd/product/PRD.md` using a safe default ID. With an identifier, it creates a named Markdown document such as `.bck-nd/product/PRD-AUTH.md`.

The generated template contains questions and placeholders. It does not fabricate product content.

### Inspect available PRDs

```console
bck-nd prd list
```

The command shows each document's ID, title, status, applicable paths, linked requirement count, and validation summary.

### Validate product context

```console
bck-nd prd validate
bck-nd prd validate PRD-AUTH
bck-nd prd validate --json
```

Human output explains actionable errors and warnings. JSON output is stable and suitable for CI.

### Change lifecycle status

```console
bck-nd prd status PRD-AUTH REVIEW
```

Status updates modify only the relevant metadata and preserve the document body, UTF-8 content, and existing line endings.

### Generate AI context

```console
bck-nd prompt .
bck-nd prompt . --no-prd
```

Valid applicable PRDs are included by default. Users can explicitly exclude product context when it is sensitive or unnecessary.

### Access through MCP

AI clients receive one new tool:

```text
get_product_context
```

The tool returns applicable PRD context, provenance, linked requirements, and validation diagnostics. Separate MCP tools for list, validation, and status management are outside the MVP.

## Product Document Contract

### Storage

- Canonical directory: `.bck-nd/product/`.
- Accepted source format in v2.5: UTF-8 Markdown with YAML front matter.
- The loader supports multiple PRDs.
- `bck-nd prd init` keeps the beginner workflow simple by creating one default document unless an ID is supplied.
- JSON is an output format, not a second editable PRD source format.

### Required metadata

- `schema_version`
- `id`
- `title`
- `status`
- `applies_to`
- `requirement_ids`

### Optional metadata

- `owner`
- `target_release`

### Required narrative sections

- Problem Statement
- Target Users
- Goals
- Non-Goals
- Success Metrics
- Scope
- Risks
- Rollout Plan
- Open Questions

### Lifecycle states

- `DRAFT`
- `REVIEW`
- `APPROVED`
- `SHIPPED`
- `ARCHIVED`

## Functional Requirements

### FR-001 — Product domain isolation

PRD models, parsing, validation, and rendering must live in a dedicated product-domain package and must not depend on Typer, MCP, or terminal formatting.

### FR-002 — Multi-document loader

The system must discover supported files directly under `.bck-nd/product/`, load them deterministically, and reject duplicate document IDs.

### FR-003 — Markdown and metadata parsing

The parser must normalize supported YAML metadata and required Markdown sections into a typed internal model. Parse failures must produce structured diagnostics rather than being silently converted to an absent document.

### FR-004 — Structured diagnostics

Every diagnostic must include a stable code, severity, message, source path, and the affected field, section, or reference when available.

### FR-005 — State-aware validation

Incomplete fields may be warnings while a document is `DRAFT`. The same omissions become blocking errors when a document enters `REVIEW`, `APPROVED`, or `SHIPPED`, according to an explicit validation policy.

### FR-006 — Requirement reference validation

Every `requirement_ids` entry must be resolved against the existing Requirements Intelligence loader. Missing references are errors. Existing requirements that are not referenced by any PRD are reported as non-blocking orphan warnings.

### FR-007 — Monorepo applicability

Each PRD must declare `applies_to` paths. `.` means the complete project. Paths must remain inside the project root and use normalized project-relative notation.

### FR-008 — Canonical renderer

One renderer must produce the canonical product representation consumed by CLI, prompt generation, MCP, and JSON serialization. Adapters must not reimplement product formatting.

### FR-009 — Prompt integration

Applicable product context must be emitted in a versioned `<product_context>` block before `<requirements_context>` and technical architecture sections. If no product files exist, no empty product block is emitted.

### FR-010 — Context provenance

Rendered product context must identify its schema version, PRD ID, lifecycle status, and project-relative source path.

### FR-011 — Context budget

Product rendering must apply a deterministic configurable character budget. Truncation must be explicit and must prioritize problem, users, goals, non-goals, metrics, linked requirements, and open questions over supporting prose.

### FR-012 — User-controlled exclusion

Prompt generation must allow product context to be excluded explicitly without deleting or modifying the source document.

### FR-013 — CLI workflow

The `prd` command group must provide `init`, `list`, `validate`, and `status`. Commands must use existing CLI conventions for paths, error codes, human output, and JSON output.

### FR-014 — MCP workflow

The MCP server must expose `get_product_context` and describe when an AI client should use it. The tool must remain read-only.

### FR-015 — Backward compatibility

Projects without `.bck-nd/product/` must retain the existing scan, prompt, requirements, MCP, and documentation behavior.

## Validation Policy

Initial diagnostic families will cover:

- Invalid, missing, or duplicate PRD identifiers.
- Unsupported schema versions.
- Invalid lifecycle states.
- Missing required metadata.
- Missing or placeholder required sections.
- Goals without measurable success metrics.
- Missing requirement references.
- Orphan requirements.
- `applies_to` paths outside the project root or paths that do not exist.
- Approved or shipped documents with unresolved blocking questions.

Diagnostic codes are public machine-readable contracts once released and must not be casually renamed.

## Context Contract

The canonical prompt representation will follow this ordering:

```text
<product_context schema_version="1">
  Product intent and provenance
</product_context>

<requirements_context>
  Detailed behavior and business rules
</requirements_context>

<project_tree>
  Current repository structure
</project_tree>

<architecture_uml>
  Current technical architecture
</architecture_uml>
```

The exact inner syntax is an implementation contract to be finalized before Sprint 1. It must remain deterministic, concise, and safe to paste into an AI conversation.

## Architecture Boundaries

- Product intent remains separate from the technical ASG in v2.5.
- Existing requirement domain models remain backward-compatible.
- The product layer references requirements by ID; requirement sources do not need a new `prd_id` field.
- A higher-level context or traceability graph may derive inverse relationships in a later release.
- CLI and MCP are adapters over the same product application service.
- Validation remains local and deterministic; no network or model call is required.

## Non-Functional Requirements

### Performance

- Parsing and validating one typical PRD should add no more than 50 ms on a normal local development machine after process startup.
- Processing 20 typical PRDs should add no more than 150 ms to prompt generation, excluding unrelated project scanning.
- A project without product documents should incur negligible measurable overhead.

### Context efficiency

- A typical single-PRD product block should remain below approximately 1,500 estimated tokens using the default budget.
- Output ordering and truncation must be deterministic.

### Reliability

- Invalid product files must not crash full project scanning or erase diagnostics.
- Status updates must preserve UTF-8 characters, unrelated Markdown content, and CRLF/LF line endings.
- All file paths must be resolved safely within the selected project root.

### Portability

- The feature must work on supported Python versions and on Windows, Linux, and macOS.
- The feature must not require a web browser, cloud account, or external service.

### Dependency policy

- No heavyweight dependency is permitted.
- The implementation should use Python standard-library facilities and the already-declared PyYAML dependency.

## Success Metrics

### Release acceptance metrics

- All existing tests remain passing.
- New product-domain behavior is covered by unit, CLI, prompt, MCP, path-safety, encoding, and backward-compatibility tests.
- Every invalid fixture produces the expected stable diagnostic code and severity.
- A valid PRD linked to valid requirements appears consistently in CLI, prompt, MCP, and JSON views.
- Projects without PRDs emit no `<product_context>` block and require no migration.
- The default product-context output for the reference PRD remains within the agreed token budget.

### Early user outcome metrics

Within 60 days of release:

- At least five independent projects adopt a version-controlled `.bck-nd/product/` document, evidenced through public repositories or voluntary user reports.
- At least five students or educators complete the `init → edit → validate → prompt` workflow.
- At least 80% of observed first-time users in a small usability session complete that workflow without direct author assistance.
- No confirmed incident reports product intent being silently fabricated or invalid PRDs being presented as approved context.

Backend Helper will not add telemetry for these metrics. Evidence will come from opt-in feedback, public repositories, classroom use, and issue reports.

## Risks and Mitigations

### Risk: Backend Helper becomes a project-management platform

**Mitigation:** Keep v2.5 limited to local files, validation, context rendering, and read-only MCP access.

### Risk: The PRD template becomes bureaucratic for students

**Mitigation:** Keep one-command initialization, plain-language prompts, state-aware validation, and one default PRD workflow.

### Risk: Product context increases token usage excessively

**Mitigation:** Use a canonical compact renderer, deterministic priority order, and a configurable budget with explicit truncation.

### Risk: Two sources repeat the same functional detail

**Mitigation:** PRDs reference requirement IDs instead of duplicating user stories, acceptance criteria, or business rules.

### Risk: Agents treat draft content as approved truth

**Mitigation:** Always include lifecycle status and validation diagnostics in rendered context.

### Risk: Multiple PRDs create ambiguous scope in monorepos

**Mitigation:** Require normalized `applies_to` paths and define deterministic selection rules.

### Risk: Sensitive product strategy is shared accidentally

**Mitigation:** Provide explicit prompt exclusion and keep MCP product access read-only and user-invoked.

## Assumptions

- PRDs are intentionally version-controlled and are not automatically added to `.gitignore`.
- PyYAML remains an accepted lightweight runtime dependency.
- Requirements continue to use the existing `.bck-nd/requirements/` storage and ID conventions.
- Most student projects begin with one PRD, while the internal model must support multiple documents.
- Product authors understand that Markdown content may be included in AI prompts unless explicitly excluded.
- Enterprise governance features will be evaluated only after the local workflow proves useful.

## Open Questions

### OQ-001 — Default identifier

When `bck-nd prd init` is called without an ID, should the generated document use `PRD` or a numbered identifier such as `PRD-001`?

### OQ-002 — Context budget configuration

Should the first release expose a dedicated `--max-product-chars` option, reuse a project configuration value, or ship only a sensible fixed default plus `--no-prd`?

### OQ-003 — Draft inclusion policy

Should `bck-nd prompt` include valid `DRAFT` documents by default with a visible warning, or include only `REVIEW` and `APPROVED` documents unless explicitly requested?

### OQ-004 — Multiple applicable PRDs

When multiple documents apply to the same path, should all be included within the shared budget, or should one document be marked as primary?

### OQ-005 — Blocking open questions

Should every open question block `APPROVED`, or should authors be able to mark individual questions as non-blocking follow-ups?
